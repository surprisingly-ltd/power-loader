How Power Loader works

You don’t need to read this to use Power Loader. It’s for the people in your organisation who approve tools like it.

This page describes how Power Loader {{VERSION}} handles data, where the boundaries between its parts are, and which controls your organisation and its forms library can apply. Each claim is true of the code in the public repository at this version. Where something has been tested only with a simulated browser, not yet in real Firefox, the page says so (what the controls don’t do).

Words with a special meaning are explained where they first appear, and again in the glossary. For the legal side, such as who is the data controller and your rights, see the privacy policy.

In brief

  • All the logic runs in the Firefox extension. There is no Power Loader server, no account, and no analytics or telemetry.
  • Case data stays in the browser’s extension storage on the caseworker’s computer, and is deleted when the case is finished or discarded.
  • Forms and profiles come from your organisation’s library: a set of static files it controls, published with a manifest that gives the SHA-256 of every file. A set with a wrong hash or an invalid file is refused.
  • AI is optional. Power Loader works with no AI at all. If your organisation sets it up, requests go only to the gateway it chooses, and only after the caseworker has seen a redaction preview of the exact request and pressed Send.
  • Your organisation and its library decide which systems Power Loader may act on, and what it may do there, with site rules that only ever narrow.
  • Your organisation decides how much Power Loader does, from locked down to smart and easy, and can lock each choice. The next section sets out the choices.

Your organisation decides what is sent where

Power Loader can run with no AI at all, and with very strict allow and deny lists. It can also use AI, optionally through your own organisation’s gateway, such as an internal AI endpoint. If it uses AI, the on-device privacy model (a privacy shield that runs on the caseworker’s computer) checks every request by default, before the caseworker sees the preview.

Each choice is made in the same order. Policy comes first, and locks what it sets. Then the library, which can lock a choice or leave it as a default. Then the caseworker, in Settings, for whatever is left open.

Power Loader with no AI

  • Remote AI is off until it is set up. No ✦ action is offered until Settings has an endpoint address and the caseworker has ticked the acknowledgement (aiReady() in lib/ai/settings.js). Until then nothing is sent to any AI.
  • Flows can be built entirely by hand. The author chooses Make it by hand, clicks each box on the form and each value on the page, writes the steps, and tests each page.
  • A case needs no AI. Clipping, auto-clip, the identity check, conflicts, the fill plan, fetch steps, notes, the site rules, the calculator and the timeline all work without it. The reader reads PDFs on this computer, and pictures and scans with OCR (Tesseract, packaged in the extension).
  • The two on-device models can be switched off too. The privacy model with policy privacyModel.use: false, and the profile assistant, which suggests fields when a profile is made without remote AI, with assistModel.enabled: false. With both off and no remote AI, Power Loader downloads no model. The only model it runs is the packaged OCR, when a caseworker reads a picture or a scanned PDF.

A flow is a set of instructions for one kind of case: the forms it fills, the pages it reads from, and the steps in between. A profile tells Power Loader where each value is on a page, with selectors, never with the values themselves. A clip is the set of values read from one page, each with the text it was read from.

Controls your organisation and library can apply

Three people can set controls: your organisation, through Firefox enterprise policy; your library, through its files; and the caseworker, in Settings. Anything set by policy is locked in the sidebar.

The layers and their order

Site rules say where Power Loader may act and what it may do there. They come in layers. A decision checks every layer, and every layer must allow the action:

{{HIW_LAYERS_DIAGRAM}}
LayerSet inWho can change itCovers
1. Enterprise policyFirefox policies.json: siteAccess.allow, siteAccess.deny, siteAccess.rulesIT only. Firefox reads it at start-up.Every action
2. The library’s locked rulesaccess.json, rules with "lock": true (or every rule, if policy sets siteAccess.lockLibraryRules)The library maintainerEvery action
3. The caseworker’s rules, and the library’s delegated rulesaccess.json rules without a lock, plus the caseworker’s own in SettingsThe caseworker can turn a delegated rule off, change it, or add their ownEvery action
4. Approved systemsapprovedHosts in the library’s library.json, or a flow’s own hostsThe library maintainerReading, filling and fetching, where a case’s library applies

Rules only ever narrow. A deny that matches, in any layer, blocks the action. A layer that has allow rules for an action must have one that matches the address; a layer with none for that action has no opinion. So adding a layer, or a rule, can only take pages away. The one exception is fetch-post, which is closed until an allow rule names it (see below). While a case is open, the locked rules of both the case’s pinned library commit and the newly synced one apply, so a deny published mid-case reaches it. The rules are read again for every action, so a change in Settings applies at once. All of this is in accessLayers() and allowed() in lib/access.js.

{{HIW_DECIDE_DIAGRAM}}

If a policy deny address can’t be read, dropping it would widen what Power Loader may do, so instead Power Loader works on no page until IT corrects it, and Settings names the address. A policy allow address that can’t be read is dropped, which narrows.

Site rules limit Power Loader, never the caseworker’s browsing. A blocked page still opens and works as normal. Power Loader just doesn’t read it, fill it, write notes on it, capture it or fetch it.

Allow and deny lists

Patterns. An address pattern is read as a web address, in its parts:

  • the scheme: https://, http://, or *:// for both;
  • the host: a name such as cases.council.example, or *.council.example for that domain and every subdomain of it. A * can only start a host;
  • an optional port, such as :8443;
  • then either *, for every page on any port, or a path starting with /, in which * stands for any run of characters. The query is part of the path.

Hosts are compared the way Firefox reads them: lower case, international names in their xn-- form. A deny written with https:// also covers http://.

Actions. Each rule can name the actions it covers: {{HIW_ACTIONS}}. A rule that names none covers all of them, except that an allow rule without actions never opens fetch-post.

ActionWhat it is
navigateOpening an address from a step link, a Go to button or a link in a note.

The background-reading switch

A fetch step fetches pages the caseworker isn’t on, from the system they are on, and clips them. One switch, Read pages in the background, covers every fetch step. It is on by default (BACKGROUND_READING_DEFAULT in lib/access.js). Off is a deny of fetch-get and fetch-post in the same rules as everything else, so there is one place that enforces it.

Who decides, first match wins:

  1. policy siteAccess.backgroundReading, true or false, which sets it and locks it;
  2. the library’s "backgroundReading": { "on": false, "lock": true } in access.json, or any library choice if policy sets siteAccess.lockLibraryRules. Between the case’s pinned library and the synced one, a locked off wins;
  3. the caseworker’s own switch in Settings;
  4. the library’s choice without a lock;
  5. the default, on.

When it is off, a fetch step says who turned it off, and the caseworker opens each page and clips it themselves.

Watching a fetch, and going back to it. While a fetch step runs, each request has a box on the page the caseworker is on, showing what came back as text (never as the response’s own HTML), with the values it reads outlined. Afterwards, View what was read opens the fetched view on Power Loader’s own case page. The whole response isn’t kept: each fetched clip keeps the text around each value it read, at most 500 characters a value and 20 KB a page. That is case data: it stays in the case, appears in no log, and is deleted when the case is finished or discarded.

Every fetch request is also limited by fixed caps (FETCH_LIMITS in lib/fetch-steps.js): 6 requests a step, and one list of at most 25 links, 60 a case in any 10 minutes, 4 at a time, 20 seconds and 2 MB each. Requests go only to the site of the tab the caseworker is on, use GET, and fail on any redirect, which is usually a sign-in page.

A fetch step can also fetch every link in a list on the page the caseworker is on, such as the messages on a page of an inbox. The addresses come from that page, not from the flow, so each one is checked before anything is fetched: it must be on the same site as the tab, match the page profile the flow’s author tested for those pages, and pass the site rules for fetch-get. Duplicates are dropped and at most 25 are kept. What each page gives is a row, not a case value, so a list of messages from different people raises no identity warning, and the step lists the rows that match its show, exactly, and marks them on the page with fixed words.

Every policy key

Policy goes under 3rdparty → Extensions → {{ID}} in policies.json. This table is generated from POLICY_DEFAULTS in lib/policy.js when the page is built, so it lists every key Power Loader reads. Setting a key also locks it. Firefox reads policy at start-up, so a change needs a browser restart.

An organisation can also build its own version of Power Loader with the same keys in a policy file built into the signed package, under its own add-on ID. That version ignores policies.json: its rules change when the organisation ships a new version. A policy file can also constrain a setting by pattern (allowed), and limit the sites the build may ever connect to, which Firefox grants at install and enforces. See docs/organisation-builds.md in the repository.

What the controls don’t do

  • They guard against mistaken or poisoned flows and libraries, not against the caseworker. A caseworker controls their own browser. They can read and copy anything they can see. Unless policy locks the library address, they can connect another library, and they can build their own flows. They can turn off or change delegated rules. Rules your organisation must enforce belong in policy, or locked in the library.
  • Firefox grants host permissions for a whole origin (a scheme and host), not for paths. Power Loader removes permissions for sites the rules block entirely, but rules about paths and actions are enforced by Power Loader’s own checks, not by Firefox.
  • The library’s hashes check integrity, not authorship. They make sure a sync is one complete, unchanged set from one commit. They are not a signature: whoever can change the files on the library host can change library.json too. Trust in the library comes from who can commit to it and from HTTPS.
  • Redaction is not guaranteed. It finds what the case, the library’s patterns and the privacy model recognise, and only the first two if the model is switched off. The caseworker’s acknowledgement says that personal data could still be sent, and the preview shows exactly what will be. A picture can’t be redacted at all, so it is sent only after a separate tick, and never if policy sets redaction.blockImages.
  • Filled values reach the page. Once a value is in a box, the casework system’s own scripts can read it, as they could if it were typed. The fill plan warns when a form is known to react to changes.
  • Some things are tested only with a simulated browser so far, not yet in real Firefox. The automated Firefox suite, run in CI on the latest Firefox and the latest ESR, covers library verification, clipping, filling, the AI preview and what is actually sent, deletion after a browser restart, OCR, model hash checks, and conflicts, a reveal rule and a fetch step’s boxes and excerpts on demo pages under a strict CSP. A separate local suite runs an organisation build in Firefox ESR, including region capture (captureVisibleTab) and clearing the case. Neither covers the site rules’ permission handling or notes yet; those are covered by unit tests with a simulated browser. In particular, whether a fetch step’s request carries the casework system’s session cookies in real Firefox is not yet verified: it is made from the content script’s isolated world (FETCH_WORLD in lib/core.js).

How to check this yourself

  • The source is public, under the Apache-2.0 licence: {{REPO}}. Power Loader’s own code is not minified or bundled.
  • Reproducible builds. CI rebuilds the extension from its source archive, as Mozilla’s reviewers do, and compares every packaged file with the CI build. Third-party files are listed with their SHA-256 in the reviewer notes.
  • The tests. pnpm test runs the unit tests, including those for this page’s samples and examples. pnpm test:firefox runs the Firefox suite described above.
  • Mozilla’s review notes are in REVIEWERS.md and on the reviewers page.

Glossary

Flow
The instructions for one kind of case: the forms it fills, the pages it reads from, and the steps between them. Exported as one powerloader-flow/1 file.
Profile
Where each value is on a page, as selectors. A page profile reads a page; a fill profile says which box gets which case field.
Clip
The values read from one page or document, each with the text it was read from.
Library
Your organisation’s forms library: static files at one commit, with a manifest listing each file’s SHA-256.
Step
One stage of a case, such as a page to visit, a page to clip, a form to fill or an email to send.
Fetch step
A step that requests pages the caseworker isn’t on, from the system they are on, when they press its button.
Note
Guidance a flow draws on a casework page, next to a box or a heading.
Redaction preview
The exact AI request, with personal data found on this computer replaced by placeholders, shown to the caseworker before anything is sent.
Gateway
Your organisation’s own AI service, which Power Loader sends approved requests to. Power Loader never talks to an AI provider directly.
Policy
Firefox enterprise policy, in policies.json or Group Policy. Settings set by policy are locked.
Origin
A scheme and host, such as https://cases.council.example. Firefox grants an extension access one origin at a time.
