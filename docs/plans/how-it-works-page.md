# How it works: a page for security, compliance and data protection

Created: 2026-11-25. Status: built (2026-11-25): `site/how-it-works.html`, `tools/how-it-works.mjs`, `tools/sequence-svg.mjs`, `site/how-it-works/` (diagram specs and samples), `tests/js/how-it-works.test.js` and `sequence-svg.test.js`. Where the code and this plan differ, the page follows the code: the acknowledgement wording is fixed in the extension, not set by policy; ✦ profile suggestions send redacted page HTML, not every value as a placeholder; pictures can be sent to AI after a tick unless `redaction.blockImages`; `fetch-post` is unused; there is no control to disconnect the library.

A page on the website, `/how-it-works`, that explains how Power Loader handles data and where its controls are. It is written for **security architects, compliance officers and data protection officers** who have to approve the tool, and it should still make sense to anyone else who uses it. It is not training: caseworkers and flow authors never need to read it, and the site doesn't point them at it as something to read first.

## Audience and tone

- **Primary readers** decide whether Power Loader can be used, and on what terms: a security architect reviewing the design, a DPO writing the DPIA, a compliance officer checking where personal data goes. They want precise claims, the boundaries between components, what is stored where and for how long, what leaves the browser and under whose control, and what the controls don't do. They will check claims against the source, so every claim must be true of the code as it is, and say so plainly when something is only planned or only verified offline.
- **Secondary readers** are caseworkers, flow authors and library maintainers who are curious. The page opens with a short note: *You don't need to read this to use Power Loader. It's for the people in your organisation who approve tools like it.* Plain British English throughout. Each technical term is explained where it first appears, and there's a short glossary at the end.
- **Same voice as the rest of the site**: short declarative sentences, no marketing language, no superlatives. Say "the extension", "your organisation's library", "your organisation's AI gateway".

## Where it goes

- A new source page, `site/how-it-works.html`, built by `tools/build-site.mjs` like the others, with the shared header and footer.
- **Not in the main tabs** (Home, Setup, Try a flow, Create a flow, Play): those are the path for users. It goes in the **footer**, next to *Privacy* and *For reviewers*, as *How it works*.
- It's linked from the places primary readers already arrive: the privacy page, the reviewers page (and `REVIEWERS.md`), and the README's Policy and AI gateway sections. On the Setup page, where a library or policy is mentioned, add at most one quiet line: *For your security team: how it works.*
- It must pass `pnpm check:site`: every link and anchor resolves, and every `powerloader.surprisingly.ltd` address exists. Example hosts on the page use reserved names (`council.example`, `cases.council.example`), never real organisations or other `surprisingly.ltd` subdomains, which the check rejects.

## Diagrams

Built (2026-11-25), and since redrawn: the sequence diagrams have labelled phases, dashed optional parts and the trust boundary marked, and four more diagrams sit beside the text they illustrate, generated by `tools/diagram-svg.mjs` from specs in `site/how-it-works/diagrams.mjs` (where data goes, the layers of site rules, how a site rule decides, and the range from locked down to smart and easy), plus what a case is on the home page. Each is drawn in a wide and a narrow layout, and tested in `tests/js/diagram-svg.test.js`.

Two sequence diagrams, as **inline SVG generated at build time** from a small declarative spec in the repo. There is no diagram library at runtime and no external resource, matching the site's other pages.
- A small generator (e.g. `tools/sequence-svg.mjs`) takes participants and messages (`{ from, to, text, kind: 'call' | 'return' | 'note', group? }`) and writes an SVG with lifelines, arrows, labels, notes and boxed groups (`alt`/`opt` for "if ✦ AI is used", "if the library locks it").
- **Accessible**:
  - each SVG has a `<title>` and `<desc>`, and text in real `<text>` elements;
  - colour is never the only cue;
  - the diagram is followed by an ordered list with the same steps in words, so the diagram is never the only way to get the information;
  - it works at narrow widths (horizontal scroll inside a figure, not page scroll) and prints legibly.
- It follows the site's style: `site/style.css` colours, one font, light and dark if the site supports both.
- The generator gets a unit test: the SVG is deterministic, every message is drawn, and labels are escaped.

### Diagram 1: building a flow

Participants: **Flow author** · **Sidebar (extension)** · **In-page agent** · **Casework page (a test record)** · **Organisation's AI gateway** (optional) · **Flow file** · **Library maintainer** · **Forms library (git)**.

The steps it must show, checked against `lib/flows.js`, `sidebar/flows.js`, `lib/drafts.js`, `lib/ai/boundary.js` and `docs/plans/flow-authoring.md`:
1. The author creates a flow in the sidebar; it's stored on this computer only.
2. On the form to fill, the agent describes the form's boxes (labels, types, options, never what's typed in).
3. *opt ✦ AI*: the sidebar builds the request, redacts personal data on this computer, and shows the preview. Nothing is sent until the author presses Send. The gateway returns field mappings.
4. On each page to clip, the author picks values, or the AI suggests selectors from the reduced page HTML, with every value Power Loader outlines and anything else found on this computer replaced by a placeholder.
5. Test on the page: each field is found once and passes its validator, and the leak check confirms no value from the page is in the profile.
6. Steps, notes, fetch steps and timelines are added. The flow is checked on every change.
7. Export: one `powerloader-flow/1` file.
8. The maintainer reviews it and commits it to the library. The manifest lists every file with its SHA-256.
9. The extension syncs the library and checks every hash and every file's schema. A bad set is refused, and the last good copy stays.

### Diagram 2: running a flow (a case)

Participants: **Caseworker** · **Sidebar (extension)** · **Site rules** · **In-page agent** · **Casework systems** · **Extension storage (this computer)** · **Target form** · **Activity log**.

The steps it must show, checked against `lib/case.js`, `lib/core.js` `ask()`, `lib/access.js`, `lib/fetch-steps.js`, `lib/teardown.js`, `lib/activity.js` and `sidebar/caseview.js`:
1. Start a case from a flow or forms. The case pins the library commit.
2. On each page, the site rules are checked before Power Loader acts (read, fill, annotate, capture). The agent re-checks the page's own address at the moment it acts.
3. Clip: values with their quotes are added to the case in extension storage, with conflict and identity checks.
4. *opt fetch step*: on the trigger page, after the caseworker presses Fetch, GET requests go to the same system, with no redirects, each checked against the rules (`fetch-get`) and the background-reading switch. They become clips like any other.
5. *opt screenshot*: OCR on this computer; values are checked by the caseworker before they're added.
6. Notes are drawn on pages from the tree; links in them are checked as `navigate`.
7. Fill the target form: a dry-run plan, then values only, into the boxes; the caseworker submits it themselves.
8. *opt email step*: the email app opens with a `mailto:` link; Power Loader sends nothing.
9. *opt ✦ AI*: only through the preview, with redaction.
10. Finish or Discard: case values are deleted. The activity log is kept without values or real addresses.

## Sections of the page

1. **In brief**: five or six sentences.
   - All logic runs in the Firefox extension, and there's no Power Loader server.
   - Case data stays in the browser's extension storage, and is deleted when the case ends.
   - Forms and profiles come from your organisation's library, a set of static files it controls, checked by hash.
   - AI is optional, goes only to your organisation's gateway, and only after a redaction preview the caseworker approves.
   - Your organisation and library decide which systems Power Loader may act on.
2. **The parts and the boundaries between them**: a table with columns component, what it does, what data it handles, and where it runs. It covers:
   - the sidebar;
   - the in-page agent;
   - the background storage writer;
   - on-device models (privacy model, profile assistant, OCR, each pinned and hash-checked);
   - the forms library;
   - the AI gateway;
   - the casework systems.
   State what each can and can't reach (for example, the in-page agent listens only to the extension, never to the page).
3. **Building a flow**: diagram 1, then its steps in words.
4. **Running a flow**: diagram 2, then its steps in words.
5. **Controls your organisation and library can apply**, the core section for primary readers:
   - **The layers and their order**: enterprise policy (`policies.json`, locks settings), then the library's rules (`access.json`, each rule locked or left to the caseworker), then the caseworker's own Settings, then the library's approved systems. Rules only ever narrow, and a deny wins in any layer. Use a table and a small diagram or nested boxes.
   - **Allow and deny lists**:
     - the pattern syntax in plain words;
     - the actions (navigate, read, fill, annotate, capture, fetch-get, fetch-post), and that fetch-post is closed unless allowed;
     - a worked example as a table of addresses against two rules, in the spirit of `site-access-lists.md` (allow `https://*.council.example*`, deny `https://finance.council.example*`);
     - an action-scoped example, as in the demo library: fetching allowed only for one service.
   - **The background-reading switch**: what it covers, its default, and who can lock it.
   - **Other controls**:
     - redaction patterns (`privacy.json`);
     - the AI gateway address and model, set or locked by policy (the acknowledgement wording is fixed in the extension);
     - turning the on-device assistant off;
     - the activity log settings;
     - the library pin (`library.*` policy).
     List each with its policy key or library file, read from `extension/lib/policy.js` and the README.
   - **A sample `access.json`** and a sample `policies.json` fragment, both valid, and checked by a test that runs them through the real validators.
6. **What leaves the browser, and when**: a table with columns destination, what is sent, triggered by whom, and controlled by.
   - Casework systems: the caseworker's own page views, plus fetch-step requests.
   - Your library host: fetching the library.
   - Hugging Face, or the model server set in Settings or policy: the model downloads.
   - The AI gateway: only after the preview.
   - Nothing to Surprisingly Ltd: say so only if the code confirms it. Check the update URL and any telemetry. Firefox's update check on `updates.json` is a request to the project site, so say exactly what it contains.
7. **What's stored, where and for how long**: the case, drafts, flows, settings, the activity log and the model caches, each with how to delete it. This draws on `docs/plans/case-activity-log.md` and the privacy page; link to the privacy page instead of repeating it.
8. **What the controls don't do**: the threat model, stated honestly.
   - They guard against mistaken or poisoned flows and libraries, not a caseworker who sets out to get round them. The caseworker controls their own browser: unless policy locks the address, they can connect another library, or delete all Power Loader data, which removes the library copy.
   - Firefox limits: host permissions are per origin, and path rules are enforced by the extension, not the browser.
   - What is verified only offline so far, such as whether fetch steps carry the session cookies.
9. **How to check this yourself**:
   - the source and its licence;
   - reproducible builds (CI job);
   - the tests (`pnpm test`, the Firefox suite);
   - AMO review notes (`REVIEWERS.md`);
   - where each claim on this page lives in the code: a short table of claims and the file that implements each.
10. **Glossary**: flow, profile, clip, library, step, fetch step, note, redaction preview, gateway, policy, origin.

## Accuracy rules for the implementer

- **Every factual claim is checked against the code at the commit you build from**, not only against the plans, many of which describe intentions. Where code and plan differ, the page follows the code, and the difference is reported.
- **No claim is stronger than the evidence.** Say "checked by offline tests" or "not yet verified in Firefox" where that's the truth, especially for the site rules' permission handling, `captureVisibleTab`, and fetch-step cookies.
- **Name real files and policy keys** in the "how to check" and controls sections, so a reviewer can follow them.
- **The samples are real**: the sample `access.json` and `policies.json` on the page are extracted from files a test validates (for example `site/samples/` or fixtures), so they can't drift.
